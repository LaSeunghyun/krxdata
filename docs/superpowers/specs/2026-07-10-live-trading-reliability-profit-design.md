# live-trading reliability + profit validation 설계

- 날짜: 2026-07-10
- 대상 repo: `C:\claudeT\files`
- 상태: 설계 승인 후 문서화

## Context

현재 `paper-swing.js` 기반 라이브/페이퍼 흐름은 수익률 이전에 안정성 문제가 먼저 보인다.

핵심 이슈는 네 가지다.

1. 동일 분기에서 같은 주문이 중복 집행될 수 있다. `LIVE_QUEUE_ONLY` 경로가 실행 락보다 먼저 주문 큐를 처리한다.
2. KST 날짜 처리가 `+9h` 보정 후 `toISOString()`에 다시 들어가면서 DB 기준 시간이 왜곡될 수 있다.
3. 백테스트/페이퍼/라이브 간 수수료·세금 반영과 체결/현금 반영 방식이 완전히 일치하지 않는다.
4. RSI2 계열의 "저가 대체 유니버스"는 검증보다 편의가 앞선 상태라, 실제 수익 개선인지 착시인지 분리할 필요가 있다.

리서치 관점에서는 다음 두 축이 유효하다.

- 시간순 모멘텀과 추세 추종은 장기적으로 의미가 있다.
- 변동성이 높은 구간에서 노출을 줄이는 볼라틸리티 스케일링은 기대값보다 분산을 먼저 줄이는 쪽으로 작동한다.

이 설계의 목표는 "기법을 더 얹는 것"보다 먼저, 현재 전략이 제대로 측정되고 안전하게 실행되도록 만드는 것이다.

## Approaches

### A. 안정성 복구 + 실험 분리

중복 주문, 시간 왜곡, 비용 반영 불일치를 먼저 고치고, 그 위에 변동성 스로틀을 실험 플래그로만 붙인다.

- 장점: 실제 손실을 만드는 구조적 버그를 먼저 제거한다.
- 단점: 단기적으로는 전략이 덜 공격적으로 보일 수 있다.
- 추천 여부: 예. 현재 상태에 가장 맞는다.

### B. 전략 교체 중심

RSI2, 돌파, 모멘텀 중 한 축을 갈아엎고 새 팩터를 추가한다.

- 장점: 이론상 더 큰 수익 기회가 있을 수 있다.
- 단점: 기존 데이터의 오염, 과최적화, 검증 비용이 크다.
- 추천 여부: 아니오. 지금은 원인 분리보다 실험 과잉 위험이 더 크다.

### C. 최소 버그 수정만 수행

중복 주문과 시간 처리만 고치고, 수익률 개선 실험은 뒤로 민다.

- 장점: 범위가 작다.
- 단점: 지금 관찰된 구조적 손실과 기회비용을 같이 방치한다.
- 추천 여부: 부분적으로만 유효하다.

선택은 A다.

## Design

### 1) 실행 안전성

라이브 주문은 "큐 처리"와 "브로커 전송" 사이에 단일 소유권을 가져야 한다.

- 각 주문에 deterministic `orderKey`를 부여한다.
- `queued -> claimed -> submitted -> filled/canceled/failed` 상태 전이를 갖는다.
- `LIVE_QUEUE_ONLY` 포함 모든 라이브 실행 경로가 동일한 실행 락을 통과해야 한다.
- 브로커 응답 전후 재시도는 `orderKey` 기준으로 멱등이어야 한다.

권장 구조는 별도 주문 상태 저장소다. 현재 메모리성 플래그에 의존하면 재시작 시 중복을 막기 어렵다.

### 2) 시간 처리

DB 저장 시각은 UTC 원본을 그대로 사용한다.

- 저장은 `new Date().toISOString()` 같은 원본 UTC를 유지한다.
- KST는 표시/집계 함수에서만 포맷한다.
- "오늘" 기준 조회는 `[KST 00:00, 다음날 KST 00:00)` 경계를 명시적으로 사용한다.

이렇게 하면 저널, 쿨다운, 거래일 집계가 서로 다른 날짜로 어긋나는 문제를 막을 수 있다.

### 3) 비용/체결 모델

백테스트, 페이퍼, 라이브는 같은 비용 모델을 공유해야 한다.

- 매수/매도 모두 수수료를 현금 흐름에 반영한다.
- 매도세는 시장별로 분리한다. 2026년 한국 주식 세율 변화처럼 실제 제도에 맞게 market-aware로 둔다.
- 체결은 next-open 기준을 유지하되, 슬리피지와 최소 호가 단위를 공통 함수로 계산한다.

라이브 체결 로그에는 최소한 다음이 남아야 한다.

- signal time
- reference price
- submitted limit
- fill price
- slippage bps
- fee/tax breakdown

### 4) 전략 정합성

라이브의 기준 전략은 이미 검증된 조합으로 고정한다.

- `COMBO_CAPS`는 라이브 기준으로 `D`를 사용한다.
- 종목이 예산을 못 맞추면 강제로 1주를 사지 않는다.
- RSI2는 "실제로 살 수 있는 대체주"가 아니라, 검증된 유니버스만 유지한다.
- 현금 보유가 더 나은 선택이면 진입하지 않는다.

이 파트의 핵심은 새 알파를 억지로 늘리는 것이 아니라, 전략 선택과 수량 계산이 서로 충돌하지 않게 만드는 것이다.

### 5) 실험용 볼라틸리티 스로틀

리서치로 반영할 수 있는 새 기법은 하나만 둔다. 과하지 않은 변동성 축소다.

- 기본 아이디어는 최근 실현 변동성이 높을수록 포지션 노출을 줄이는 것이다.
- 레버리지는 쓰지 않는다.
- 하한선은 두지 않거나 매우 보수적으로 둔다. 현금으로 빠지는 쪽을 허용한다.
- 실거래 적용 전에는 반드시 shadow 모드로만 검증한다.

이 실험은 전략 교체가 아니라 "노출 조절"로 취급한다.

## Data Flow

1. 시그널 생성
2. 주문 키 생성
3. 실행 락 획득
4. 주문 상태 claimed
5. 브로커 전송
6. fill/failed 정산
7. 저널 저장
8. 백테스트/페이퍼 리포트 갱신

이 흐름에서 어느 단계가 실패했는지 추적할 수 있어야 한다.

## Error Handling

- 토큰 만료나 인증 오류는 주문 무결성 오류와 분리한다.
- 인증 실패 시 신규 매수만 멈추고, 기존 포지션 관리와 정산 조회는 유지한다.
- 중복 감지가 되면 새 주문을 내지 않고 기존 주문 상태를 확인한다.
- 실행 중 크래시가 나면, 재시작 후에는 브로커 실제 상태를 기준으로 복구한다.

## Testing

설계가 구현되면 다음 테스트가 필요하다.

- `LIVE_QUEUE_ONLY`가 실행 락 없이 주문을 내지 않는지
- 같은 `orderKey`가 두 번 브로커로 전송되지 않는지
- 크래시 후 재시작 시 중복 주문이 생기지 않는지
- KST 저널 날짜가 UTC 저장 시각과 충돌하지 않는지
- 매수/매도 현금 흐름에 수수료와 세금이 실제로 반영되는지
- market-aware 세율이 시장별로 다르게 적용되는지
- 강제 1주 보정이 사라졌는지
- 라이브/백테스트가 같은 유니버스와 같은 비용 모델을 쓰는지

성능 지표는 아래 순서로 본다.

1. 오류율과 중복 주문 0 여부
2. 순손익
3. 승률보다 PF와 MDD
4. 변동성 스로틀의 shadow 결과

## Rollout

1. 실행 안전성 수정
2. 시간/비용 정합성 수정
3. 전략 상수 정렬
4. 볼라틸리티 스로틀 shadow 실험
5. 충분한 거래 수 이후에만 enable 여부 판단

실제 라이브 상태 변경은 이 설계 범위에 포함하지 않는다. 5.4 구현 단계에서만 진행한다.

## Handoff

5.4가 구현할 때의 예상 파일 범위는 다음과 같다.

- `paper-swing.js`
- `backtest-swing.mjs`
- `slot-alloc.js`
- `config.js`
- 신규 공통 모듈 1~2개
- 테스트 파일 2~4개

설계의 판정 기준은 "더 많이 사는 것"이 아니라 "같은 조건에서 같은 결과가 재현되는가"다.
